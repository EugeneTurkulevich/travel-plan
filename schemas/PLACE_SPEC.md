# Специфікація картки бібліотеки

Картка (`places/<id>.md` у даних) описує **місце**, а не поїздку. Один
слуг — один файл, живе скільки завгодно поїздок довше за будь-який
конкретний маршрут (`STRUCTURE_PROPOSAL.md` §4, §5.1).

Ця специфікація — рівень 2 (тулкіт): вона описує *форму* картки й
*механізм*. Самі картки, самі категорії POI конкретної подорожі й самі
overlay-файли — рівень 3 (`../travel-data/`), сюди не потрапляють.

---

## 1. Обов'язкові рядки метаданих

Перший блок картки — двоколонкова таблиця `## Метадані`:

```
## Метадані

| | |
|:--|:--|
| **ID** | `<стабільний slug>` |
| **Глибина** | ескіз / базовий / повний |
| **Країна** | <назва країни з емодзі прапора> |
| **Код** | <ISO 3166-1 alpha-2> |
| **Координати** | <lat>, <lon> |
| **Google Maps** | [відкрити](https://www.google.com/maps?q=<lat>,<lon>) |
| **ЮНЕСКО** | так / ні (опційно — коротке пояснення в дужках) |
```

| Рядок | Навіщо |
|:--|:--|
| **ID** | Стабільна ідентичність картки. **Не ім'я файлу** — файл можна перейменувати, `ID` лишається тим самим рядком, на який посилається `route.json`, `poi_categories`-звірка, гейт публічності (харвест геоназв) і будь-який інший скрипт, що читає бібліотеку. |
| **Глибина** | Одне зі значень «ескіз» / «базовий» / «повний» — див. §2. Це поле, а не окремий прапорець, бо глибина застосовується до картки цілком. |
| **Країна** / **Код** | Country name + ISO alpha-2. Код — машинний ключ (використовується там, де потрібна дизамбігуація запитів чи угруповання), назва — те, що бачить людина. |
| **Координати** | Базова точка картки (зазвичай центр міста/локації) — те, що йде на карту, якщо `route.json` не перекриває `lat`/`lon` для конкретного дня (`route.schema.json`). |
| **Google Maps** | Пряме посилання, будується з тих самих координат — зручність, не окреме джерело істини. |
| **ЮНЕСКО** | Так/ні з опційною приміткою — часто впливає на вартість/розклад відвідування, тому винесено в метадані, а не сховано в прозі. |

Рядок **«Звірено з картою»** (дата) — необов'язковий, зʼявляється, коли
картку звіряли з живим станом карти (`/audit`); формату метаданих не
змінює.

## 2. Три рівні глибини

Глибина — **властивість картки, яка тільки росте**: ескіз сьогодні,
повний — коли місце дійшло до маршруту, і ніколи назад. Методичка
воркера радить готувати кандидатів ескізом і доводити до повного лише
тих, хто реально потрапив у маршрут — «повна картка десяти кандидатів,
з яких візьмуть два» назва марнотратством прямим текстом.

Три назви й три пороги — той самий поділ, що й у методичці воркера для
точок на карті (`trip-map://guide`, розділ про глибину проробки); тут —
його відповідник для MD-картки бібліотеки:

| Рівень | Що є | Коли досить |
|:--|:--|:--|
| **ескіз** | Метадані + координати + короткий `## Опис` (1–2 речення «чому це може бути цікаво»), без POI-таблиць, без фото | Кандидат, якого ще не обирали — досить, щоб власник побачив, що саме пропонують, і оцінив зірочками |
| **базовий** | Метадані + повний `## Опис` + базова POI-секція з кількома (2–3) ключовими POI, без фото; решта секцій (`Де зупинитись`, `В'їзд на авто`, `Паркування`, `Практичне`, `Нотатки`) можуть бути відсутні або неповні | Це і рівень, на якому автоматично народжуються картки після імпорту з карти чи синхронізації (`popup_html`, згенерований HTML, не розбирається назад у прозу — розбір завжди зупиняється на «базовому»), і розумний проміжний крок ручної підготовки кандидата |
| **повний** | Усі секції заповнені: опис, повна POI-секція з фото, будь-які категорії з `poi_categories` цієї поїздки, практичні секції, нотатки | Обов'язково для ролі `overnight` у маршруті (і будь-якої ролі, де на картку спираються в дорозі, а не лише як на довідку «є такий кандидат») |

Глибину нарощують поступово, а не переробляють з нуля — методичка й
тут явна: «ескіз доводиться до повної картки», не переписується. Усі
наявні картки бібліотеки на момент написання цієї специфікації —
`повний` (місця вже пройшли добір у маршрут чи в альтернативи); рівні
«ескіз»/«базовий» описано тут наперед, за методичкою, а не за
прикладом, якого поки нема в даних.

**Повнота — властивість пари (місце, роль, глибина), не тільки
картки.** Одна й та сама картка може бути достатньою для ролі `visit`
і недостатньою для `overnight` того ж місця в іншій поїздці —
рішення ухвалює `/place` під конкретну роль, не спец.

## 3. Секції картки і механізм «секція ↔ категорія»

Фіксовані секції картки (є завжди, незалежно від поїздки):

`## Опис` · базова POI-таблиця (категорія `poi`, завжди присутня для
всіх поїздок однаково) · `## Де зупинитись` · `## В'їзд на авто` ·
`## Паркування` · `## Практичне` · `## Нотатки`

Формат POI-таблиці (базової і будь-якої категорійної, див. нижче):
стовпці `Назва`, `Опис`, `lat, lon` обов'язкові, `Фото` — опційний
додатковий стовпець, коли посилання є.

### Механізм додаткових категорій

Понад фіксовані секції картка може мати секції під **категорії POI
конкретної поїздки** — сувеніри, місцева їжа, оглядові точки, що
завгодно. ⚠️ **Самі категорії тут не перелічуються** — це данні
профілю: `poi_categories` у `trip.json` (`../travel-data/`, схема —
`trip.schema.json`). Тут документується лише механізм, яким одне
перетворюється на інше.

Кожен запис `poi_categories.<ключ>` несе `icon` (емодзі) і `section`
(точний текст заголовка MD-секції, без іконки й без `##`). Картка додає
секцію `## <icon> <section>` з тим самим текстом, і генератор
(`generate_state.py`) при складанні `route_state.json` розпізнає її й
випускає для кожного рядка таблиці `type` (машинний ключ категорії),
`type_name` (текст, який бачить людина в попапі) і `type_icon` (та сама
іконка) — саме ці три поля бачить `add_poi`/`nested_points` на карті.

**Приклад із вигаданою категорією** (не з жодної реальної поїздки):

```json
// trip.json (дані)
"poi_categories": {
  "morning_pastry": { "icon": "🥐", "section": "Ранкова випічка" }
}
```

```markdown
<!-- places/<id>.md (дані) -->
## 🥐 Ранкова випічка

| Назва | Опис | lat, lon |
|:------|:-----|:---------|
| **Приклад пекарні** | ... | 12.34, 56.78 |
```

Генератор бачить секцію «Ранкова випічка», зіставляє з
`poi_categories.morning_pastry.section`, і кожен рядок таблиці стає
POI з `type: "morning_pastry"`, `type_icon: "🥐"`.

⚠️ **Практичне обмеження поточної реалізації.** `type_name` (текст
попапу) `generate_state.py` бере не з `trip.json`, а з власного
фіксованого словника ключ→підпис — це **механізм генератора**, не дані
(задокументовано і в коментарі самого скрипта, і в `check_no_data.py`,
і навмисно винесено з-під гейту публічності саме тому, що це код, а не
чиясь поїздка). Практичний наслідок: сьогодні генератор розпізнає
наперед відому невелику множину ключів категорій із конфігурованими
`icon`/`section`; зовсім новий ключ категорії, якого раніше не було,
потребує додати рядок у цей словник **у коді генератора**, а не лише в
`trip.json`. Методичка воркера трактує `type`/`type_name`/`type_icon`
як цілком довільні на рівні самого `add_poi` (там обмеження справді
нема) — розбіжність варта знати, а не приховувати.

**`needs_overnight`** — прапорець на категорії в `poi_categories`, який
каже «ця категорія відкрита лише для точок з ночівлею». Ставиться
**виключно** якщо категорія явно оголошена такою в `trip_rules` карти
(`get_map`) — вгадувати заборонено методичкою: чи є щось «вечірньою»
категорією, залежить від конкретної поїздки, і на кожній вгадав би
інакше.

## 4. Чого в картці бути не може

Картка описує те, що вірне **незалежно від поїздки**. Тайминги,
бронювання і день-індексована проза належать `route.json`/overlay і
не потрапляють у картку:

- `Тип`, `Тайминг`, `Дата` — рішення конкретного маршруту (`route.json`
  `days[].points[].kind`/`arrive_at`);
- `Бронь`, `Час перебування` — `route.json`
  `booking_note`/`stay_minutes`;
- `## Суміжні місця` — прив'язка до сусідів у конкретному маршруті, не
  властивість самого місця;
- день-індексована проза («тут ми стоїмо дві ночі», «приїзд о...») —
  живе в overlay поїздки, не в картці.

Ознака, що щось потрапило в картку помилково: якщо прибрати цю поїздку
й уявити картку в **іншому** маршруті — речення перестає бути вірним.
Це і є перевірка «незалежно від поїздки».

## 5. Картка + overlay = попап

Картка сама по собі — не те, що піде в попап конкретної поїздки.
`generate_state.py` зшиває картку з overlay-файлом
(`trips/<профіль>/overlay/<id>.md`, є не в кожного місця) — але
**зшивається сьогодні рівно одна секція, не «усе, що назвати
доповненням»**. Перевірено за кодом (`generate_state.py`), не за
уявленням про те, як мало б бути:

- **`## Опис`** картки + **`## Опис (доповнення)`** overlay (якщо є) —
  об'єднуються пробілом в один абзац попапу (`get_section` картки +
  `get_section` overlay). Overlay тут не переписує картку, а додає до
  неї те, що вірне тільки для цієї поїздки.
- POI-таблиці (базова й будь-яка з `poi_categories`), **`## Де
  зупинитись`**, **`## В'їзд на авто`**, **`## Паркування`** —
  беруться **лише з картки**; overlay для них жодного «(доповнення)»
  не читає, навіть якщо такий заголовок є у файлі overlay.
- **`## Практичне`** картки й overlay-секції **`## Практичне
  (доповнення)`** / **`## Нотатки дня`** генератор **не читає
  взагалі** — ні з картки, ні з overlay. Ці заголовки трапляються в
  реальних overlay-файлах (людина їх пише), але сьогодні це проза для
  людини, яка відкриє MD напряму, а не вхід у попап. Якщо колись
  зʼявиться потреба показувати це в попапі — це зміна коду
  `generate_state.py` (нова секція для зшивання), а не лише дописування
  MD.

Overlay — необов'язковий: місце без специфіки цієї поїздки просто не
має файлу в `overlay/`, і генератор бере картку без доповнень (для
`## Опис`) чи взагалі без цих секцій (для `## Практичне`/`## Нотатки
дня`, яких генератор не бачить незалежно від overlay).
