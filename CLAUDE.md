# Claude Code rules — travel-plan

Тулкіт для планування авто-подорожей поверх спільної карти
[trip-map](https://trip-map.web.app) і її MCP-воркера.

⚠️ **Чернетка Ф0.** Остаточна редакція — Ф7 плану міграції. Зараз тут рівно те,
без чого не можна працювати в перехідний період.

---

## 0. Три рівні — головне правило

| Рівень | Де | Що там |
|:--|:--|:--|
| **воркер** | `trip-map-mcp.e--t.workers.dev`, репо `../map-server` | те, що працює для **всіх** користувачів карти. Чужа зона |
| **тулкіт** | цей репозиторій, публічний | правила, скрипти, скіли, схеми |
| **дані** | `../travel-data/` (див. `.travel-local.json`) | зібрані місця, маршрути, привʼязки, кеші, токен. Приватне |

**У цьому репозиторії не може бути даних.** Ні `map_id`, ні назв міст, ні
таймінгів, ні категорій POI конкретної поїздки. Правила — так, екземпляри — ні.
Якщо кортить щось «тимчасово покласти поруч» — це ознака, що воно належить
кореню даних.

**У чужу зону не пишемо.** Діагностику для воркера оформлюємо як задачу: файл у
`../map-server/docs/` + рядок у його `TODO.md`. Ніколи код.

Повний контекст рішень — [STRUCTURE_PROPOSAL.md](STRUCTURE_PROPOSAL.md),
порядок робіт — [MIGRATION_PLAN.md](MIGRATION_PLAN.md).

## 0.1. Делегування розробки

**Проєктуєш → передаєш на реалізацію молодшим агентам → перевіряєш.**

Написання коду йде через Agent tool: звичайні задачі — `model: "sonnet"`,
надскладні (протоколи, великі модулі, незворотні перетворення даних) — `opus`.
Старша модель не пише код руками, а:

1. **проєктує** — детальна специфікація: що на вході, що на виході, точний
   формат, перелік файлів, які агент має прочитати для контексту, критерії
   приймання;
2. **делегує** — один агент на одну звʼязну задачу;
3. **перевіряє** — читає результат, ганяє наживо, звіряє з критеріями,
   робить дрібні правки сам (кілька рядків), веде документацію й комітить.

Агент після написання коду обовʼязково проганяє `python3 -m py_compile` і
звітує про **відхилення від специфікації**, а не лише про успіх.

Дрібні правки (перейменувати константу, поправити рядок) роблю сам — заводити
агента на два рядки дорожче, ніж зробити.

## 1. Перед будь-яким плануванням

**Методичка воркера — `trip-map://guide`.** Це канон: модель карти, ревізії й
`base_rev`, глибина проробки, альтернативні точки, замок на бронюваннях,
нормативи таймінгу, етикет. **Не дублюй її тут** — читай першоджерело, воно
змінюється.

**`trip_rules` на карті** (`get_map`) — правила саме цієї подорожі, вони мають
пріоритет над дефолтами методички. Живуть не в репо і не в даних: власник
міняє їх без нас.

**`server_tools_rev`** з `get_map` звіряй з ревізією набору тулів, названою в
інструкціях підключення. Не збігається — набір застарів: скажи користувачу
перепідключити конектор (`/mcp`) і попередь **один раз за сесію**, що працюєш на
старому наборі. Це не теорія й не разовий випадок, а регулярна подія:
04.08.2026 правила проєкту описували 30 тулів, тоді як воркер віддавав 37;
07.08.2026 конектор сесії був підключений на ревізії 42, а воркер уже
віддавав 49 (`rebuild_segment`); 08.08.2026 — з 49 на 52 (`get_route_brief`,
`list_alt_route_brief`, `get_point` — легкі варіанти read-тулів без важкого
вмісту точки, для орієнтації без витрат контексту). Перевіряй щоразу, а не
лише «якщо щось здається дивним».

⚠️ **Номер ревізії не змінюється — не означає «нічого не змінилось».** Той
самий день, 08.08.2026: хеш `server_tools_rev` перейшов з `52:1yl7viy` на
`52:5l663r` — номер тулів той самий (52), а поведінка вже наявних тулів
змінилась (`move_point` став автопідлаштовувати дату, `create_map` став
недоступний токенам з per-map OAuth-скоупом). Звіряй увесь рядок
`server_tools_rev` цілком, не лише число до двокрапки.

## 2. Активний профіль — називай його на початку сесії

```bash
python3 scripts/trip.py            # хто активний
python3 scripts/trip.py list       # усі профілі
python3 scripts/trip.py use <id>   # перемкнути
```

- Кожен скрипт друкує профіль першим рядком: `▶ <id> (map …)`.
- Зайшла мова про **іншу** поїздку — перемкнись **явно** і скажи про це.
  Мовчки працювати «в тій, що була» не можна: від профілю залежить, у яку
  карту піде публікація.
- Жодного `Path("places/…")` у скриптах — тільки через `trip_ctx`.

## 3. Перехідний період: де зараз джерело істини

Іде міграція з `../travel202609`. **До проходження гейту 2 джерело істини —
карта, а робочий канал до неї — старий репозиторій.**

- Реальні зміни маршруту робимо `../travel202609`, як і раніше.
- Тут — будуємо структуру й перевіряємо читанням.
- **З цього репо в карту нічого не пишемо**, поки `plan_push.py --dry-run` не
  дасть порожній план. Причина — не обережність заради обережності: повний
  `set_route` не переносить зниклі точки в альтернативи, і рейтинги з тредами
  під їхніми `id` зникають безповоротно.

Читати карту звідси можна й треба — це безпечно і це наш спосіб перевірки.

## 4. Скрипти

Усі в `scripts/`, запуск з кореня репо, **тільки stdlib**. Статуси (що лишається
в нас, що йде у воркер, що зламане) — [`scripts/README.md`](scripts/README.md).

Секрети — у `.env` **кореня даних**, не тут. Токен ніколи не друкуємо.

## 5. README — дві мови, одна пара

`README.md` (українська) і [`README.en.md`](README.en.md) (англійська) —
людські вітрини репозиторію, для роботи через агента (мета 08.08.2026:
цим тулкітом має вільно користуватись англомовна людина, спілкуючись зі
своїм агентом англійською — скіли й `CLAUDE.md` лишаються українською,
бо їх читає агент, а не людина напряму, і мова агента не залежить від
мови інструкцій).

Зміна в одному README (новий розділ, оновлена команда, інша структура) —
**завжди** та сама зміна в другому, тим самим комітом. Один файл без
пари — це те, що ловить `check_no_data.py` для даних: розбіжність, яку
не видно, доки хтось не звірить руками. Не переклад слово-в-слово — той
самий зміст і структура, природною мовою кожної версії.
